# DBMS concepts in TRACE: a presentation guide

Every concept below is used for real in TRACE, and each one is tied to something you can **show** in the app. The **Database** page, and the "How the database does this" panel at the bottom of every page, show the matching SQL live.

Suggested demo order (about 10 minutes): Home → Projects → New project (constraints) → Session (junction tables) → build a chain → Evidence trail (recursive CTE) → Database page (views, query lab) → `sql/03_security.sql` (security).

---

## 1. Data modelling

| Concept | Where it is in TRACE | What to show |
| --- | --- | --- |
| **Entity / table** | 12 entity tables: `research_project`, `observation`, … | Database page → Schema |
| **Primary key** | `id bigint generated by default as identity` on every entity | Schema diagram: PK tags |
| **Composite primary key** | Every junction table, e.g. `primary key (session_id, participant_id)` | Try adding the same participant twice: the database won't allow it |
| **Foreign key, one-to-many (1:N)** | `research_session.project_id → research_project.id` | A project page lists its sessions |
| **Many-to-many (M:N)** | 9 junction tables, e.g. `participant_segment`, `observation_finding` | Database page → Junction tables |
| **Surrogate vs natural keys** | `id` is surrogate; `participant_code` is a natural key with a UNIQUE constraint | People page |
| **Normalisation (3NF)** | `observation` has no `project_id`: the project is found through its session | Record page panel shows the JOIN that derives it |
| **Data minimisation** | `participant` has no name, email or phone columns | People page note |

## 2. Integrity constraints

| Concept | Example | What to show |
| --- | --- | --- |
| **NOT NULL** | `research_objective text not null` | Submit an empty project form |
| **CHECK** | `status in ('planned','active','paused','completed')`, `end_date >= start_date`, `participant_code ~ '^P-[0-9]{2,3}$'` | Type "Alice" as a participant code |
| **UNIQUE (case-insensitive)** | `create unique index … on research_project (lower(title))` | Create "MOBILE BANKING ONBOARDING": it's refused |
| **DEFAULT** | `status default 'planned'`, `created_at default now()` | New records get dates automatically |
| **Referential actions** | `ON DELETE RESTRICT` for entities, `ON DELETE CASCADE` for junction rows | Explain why projects are archived instead of deleted |

## 3. Triggers and functions

| Concept | Example | What to show |
| --- | --- | --- |
| **BEFORE UPDATE trigger** | `trace_touch_updated_at` keeps `updated_at` current | Edit a record; "Last updated" changes |
| **Validation trigger** | `trace_check_same_project`: links can't cross projects | Linking options only show records from the same project; the database enforces it too |
| **Business-rule trigger** | `trace_block_archived_project`: archived projects accept no new work | Archive a project: the add buttons disappear, and the database refuses inserts |
| **Stored function** | `trace_lineage(type, id)`, `trace_is_editor()` | Database page → Query lab → lineage |

## 4. Queries

| Concept | View or query | Where it shows in the app |
| --- | --- | --- |
| **SELECT / WHERE (selection)** | Filters by status, project, participant | Every filter and tab |
| **Projection** | Only some columns are shown in cards | Library cards |
| **INNER JOIN** | Session → method, researcher | Session page |
| **LEFT JOIN** | `v_project_summary` keeps projects that have no lead | Projects list |
| **Multi-table JOIN** | `v_decision_strength`: decision → recommendation → insight → finding → observation | "Strongest decisions" chart on the Evidence trail |
| **Aggregate functions** | `COUNT`, `COUNT(DISTINCT …)`, `MIN` | Home totals, rings, charts |
| **GROUP BY** | `v_sessions_by_month`, `v_participants_by_segment` | Column charts, segment bars |
| **FILTER clause** | `count(*) filter (where sentiment = 'negative')` | Sentiment donuts |
| **Subqueries** | Correlated subqueries in `v_project_summary` | Projects list counts |
| **Anti-join (NOT EXISTS)** | `v_evidence_gap` | "Gaps to close" on the Evidence trail |
| **UNION ALL** | `v_evidence_record` (5 tables → 1 list), `v_evidence_edge` (4 junctions → 1 edge list) | Library "All evidence" tab |
| **Recursive CTE (WITH RECURSIVE)** | `trace_lineage` walks the evidence graph up and down | **Evidence trail** (the signature feature) |
| **Views** | 9 views in `sql/06_views.sql` | Database page → Query lab |
| **Pattern matching (ILIKE)** | Search across titles and text | Library search |
| **Date functions** | `date_trunc('month', session_date)` | Sessions per month |

## 5. Transactions and storage

| Concept | Where | Talking point |
| --- | --- | --- |
| **Transactions (BEGIN / COMMIT)** | Every install script is wrapped in a transaction | If anything fails, nothing is half-installed |
| **Atomicity, and where it's missing** | Saving a record and its links takes two requests | TRACE tells you if the links failed. A stored procedure would make it atomic: a good "future work" point |
| **Sequences / identity** | `setval(...)` after loading seed data with fixed ids | Why new rows don't clash with seeded ids |
| **Indexes** | Indexes on foreign keys and dates (`sql/02`) | Keep JOINs and "recent" lists fast as data grows |

## 6. Security

| Concept | Where | What to show |
| --- | --- | --- |
| **Roles** | `anon` (visitors) and `authenticated` (signed in) | Explain with `sql/03_security.sql` (the browser demo has no sign-in) |
| **GRANT / REVOKE** | `03_security.sql` revokes everything, then grants exactly what's needed | Nobody can DELETE projects through the API |
| **Row Level Security (RLS)** | Policies on every table, e.g. "editors can insert" | Show the policies in `sql/03_security.sql` and the SQL tests that prove them |
| **Security definer function** | `trace_is_editor()` reads a table that's otherwise hidden | The editor list itself can't be read |
| **security_invoker views** | Views run with the caller's permissions, so RLS still applies | `sql/06_views.sql` header |
| **Principle of least privilege** | Visitors can SELECT, editors INSERT/UPDATE, nobody DELETEs entities | Security table in the README |
